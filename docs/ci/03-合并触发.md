# 03 - 合并触发（PR 相关）

> 一句话：**一个 PR 从开到合并，会触发两次构建 —— 开的时候一次，合进去之后又一次。这俩是不同事件，别搞混。**

## 哪些事件属于这类

| 事件 | 什么时候触发 |
|---|---|
| `pull_request` | PR **打开**，或往 PR 分支**推新提交** |
| `pull_request_closed` | PR **关闭或合并** |
| `pull_request_metadata` | PR 标题、正文、标签、里程碑改动 |

## 最容易讲错的一点

**合并 PR 会触发两个不同的事件：**

```
点 Merge pull request
   ↓
   ├─→ pull_request_closed    PR 本身关闭了
   │
   └─→ push                   合并产生的提交落到了目标分支
```

所以哪怕你的配置里**完全没写** `pull_request_closed`，只要写了 `push`，合并之后照样会跑一次 —— 因为合并的本质就是往目标分支推了提交。

这点必须讲清楚，不然演示时看到"合并后跑了一次"，容易误以为是 `pull_request_closed` 的功劳。

## 完整时间线

以当前配置 `event: [push, manual, pull_request]` 为例：

| 时刻 | 动作 | 触发事件 | 我们跑吗 | 跑的是什么代码 |
|---|---|---|---|---|
| 1 | 开 PR | `pull_request` | ✅ 跑 | PR 分支 + 目标分支的**合并预演**结果 |
| 2 | 往 PR 推新提交 | `pull_request` | ✅ 跑 | 同上，用新提交 |
| 3 | 改 PR 标题 | `pull_request_metadata` | ❌ 不跑 | — |
| 4 | 点 Merge | `pull_request_closed` | ❌ 不跑 | — |
| 5 | 合并提交落到 master | `push` | ✅ 跑 | 合并后的 master |

**第 1 步和第 5 步跑的代码是不一样的**，这是 PR 构建的意义所在：第 1 步验证的是"合进去会不会坏"，第 5 步验证的是"真合进去之后确实没坏"。中间如果目标分支被别人推了新东西，两次结果可能不同。

## 配置怎么写

只在 PR 打开时跑（最常见，用来做合并前检查）：

```yaml
when:
  - event: pull_request
```

PR 检查 + 合并后跑：

```yaml
when:
  - event: [pull_request, push]
```

区分"检查"和"发布"两个步骤 —— 实际项目里更常这么写：

```yaml
steps:
  - name: 检查
    image: alpine
    commands:
      - echo "跑测试、跑 lint"
    when:
      - event: pull_request        # 只在 PR 阶段跑

  - name: 发布
    image: alpine
    commands:
      - echo "部署上线"
    when:
      - event: push
        branch: master             # 只在合进 master 后跑
```

这个例子最能说明 `when` 的用处：**同一份配置，两个步骤，各跑各的时机。** 检查步骤在合并前拦人，发布步骤只在真的合进主干后才动。

## 只想在"合并成功"时跑

`pull_request_closed` 有个坑：**PR 被关闭但没合并，也会触发它。** 想只在真正合并时跑，用 `evaluate` 判断环境变量：

```yaml
when:
  - event: pull_request_closed
    evaluate: 'CI_PIPELINE_EVENT == "pull_request_closed" && CI_COMMIT_PULL_REQUEST_MERGED == "true"'
```

演示时这条可以略过，属于进阶用法。实践中更省事的做法是直接用 `event: push` + `branch: master`，效果差不多且不用记变量名。

## 演示步骤

比较费时间，时间紧就只讲不做。

```bash
git checkout -b demo-pr
# 改点东西
git commit -am "演示 PR 触发"
git -c http.proxy=http://127.0.0.1:7890 push origin demo-pr
```

然后去 GitHub 开 PR → 看 Activity 出现 `pull_request` 记录 → 点 Merge → 看又出现一条 `push` 记录。

Woodpecker 的 **Pull requests** 标签页会单独列出 PR 的构建，可以顺便点开看看（现在是空的，因为还没开过 PR）。
